## 一、项目背景与目标

### 1.1 背景
大模型能力已渗透到日常学习与工作，但用户面临的现实问题是：**模型分散在不同平台**——远端 API 能力强、按量计费；本地微调模型贴合个人/垂直领域数据、免费且隐私可控。现有网页版聊天工具要么只能用一个模型，要么无法接入自己训练的模型。

### 1.2 目标
构建一个 Web 端 AI 聊天系统，**同一套对话界面内可自由切换远端大模型与本地微调模型**，并具备完整的账户体系与对话管理能力。

### 1.3 项目价值
| 维度 | 价值 |
|---|---|
| 能力 | 一个入口聚合多模型，按场景选择最合适的模型 |
| 隐私 | 本地模型完全离线推理，数据不出本机 |
| 成本 | 日常问答用本地模型，复杂任务再调远端 API |
| 教学 | 完整串联「训练 → 部署 → 接入 → 前端交互」全链路 |

### 1.4 非目标（本期不做）
- 多用户协作 / 分享会话
- 移动端 App、小程序
- 模型在线训练、微调任务调度
- 多模态（图片、语音）输入输出
- 计费与配额系统

## 二、用户与场景

### 2.1 用户画像
| 类型 | 特征 | 核心诉求 |
|---|---|---|
| 学生 / 开发者 | 有自己的微调模型 | 把本地模型接进好看的界面，随时切换 |
| 普通使用者 | 只用过网页版 AI | 界面简单、响应快、历史会话可管理 |
| 课程评审 | 检查功能完整性 | 功能全、UI 美观、密码安全、有文档 |

### 2.2 典型场景
**场景一：日常问答走本地**
> 用户打开系统，选「本地模型 Qwen-LoRA」，问课程概念。请求走本机 GPU，零成本、断网也能用。

**场景二：难题切远端**
> 同一段对话里，用户发现本地模型答得不够好，在顶部下拉切换到「DeepSeek」，**上下文继续保留**，直接追问。

**场景三：会话管理**
> 用户按主题建了多个会话，把「论文思路」重命名为「毕业论文-第三章」，删掉测试用的废弃会话。

**场景四：改密码**
> 用户觉得初始密码太弱，在个人中心修改密码，旧密码校验通过后新密码立即生效，旧 Token 全部失效。

## 三、功能需求

### 3.1 功能清单

#### （1）账户与安全
| 编号 | 需求描述 | 优先级 |
|---|---|---|
| FR-01 | 用户注册：用户名 + 密码 + 昵称，用户名唯一 | Must |
| FR-02 | 用户登录，签发 JWT，有效期 7 天 | Must |
| FR-03 | 密码**存储**使用 bcrypt 加盐哈希，数据库中不出现明文 | Must |
| FR-04 | 密码**传输**使用 RSA-OAEP 公钥加密后提交，不走明文 | Must |
| FR-05 | 查看 / 修改个人信息（昵称、邮箱、头像、个性签名） | Must |
| FR-06 | 修改密码：校验旧密码，新密码强度校验（≥8 位，含字母+数字） | Must |
| FR-07 | 修改密码后，该用户所有已签发 Token 失效 | Should |
| FR-08 | 退出登录，清除本地 Token | Must |

#### （2）模型接入与管理
| 编号 | 需求描述 | 优先级 |
|---|---|---|
| FR-09 | 远端模型：接入国内大模型 API（OpenAI 兼容协议，DeepSeek / 通义 / 智谱可配） | Must |
| FR-10 | 本地模型：加载魔塔（ModelScope）基座 + LoRA adapter / 全量 pt 权重 | Must |
| FR-11 | **自动识别加载**：扫描模型目录，自动判断是「LoRA adapter」「全量 pt」「save_pretrained 目录」并选择对应加载方式 | Must |
| FR-12 | 模型列表接口：返回模型 id、显示名、类型（remote/local）、状态（已加载/加载中/未加载） | Must |
| FR-13 | 本地模型懒加载：首次使用时加载，加载过程前端可见 | Must |
| FR-14 | 支持运行时切换模型，互不影响 | Must |
| FR-15 | 模型加载失败时给出可读的错误原因（显存不足 / 文件缺失 / 版本不匹配） | Should |

#### （3）对话管理
| 编号 | 需求描述 | 优先级 |
|---|---|---|
| FR-16 | 新建对话，自动生成标题（首条消息前 20 字） | Must |
| FR-17 | 对话列表按更新时间倒序展示 | Must |
| FR-18 | 重命名对话（行内编辑） | Must |
| FR-19 | 删除对话（二次确认，级联删除消息） | Must |
| FR-20 | 会话内**切换模型**，历史消息保留，后续消息用新模型 | Must |
| FR-21 | 每个会话记录「当前使用的模型」 | Must |

#### （4）聊天交互
| 编号 | 需求描述 | 优先级 |
|---|---|---|
| FR-22 | 发送消息，**流式输出**（SSE），逐字显示 | Must |
| FR-23 | 支持中断生成（停止按钮） | Must |
| FR-24 | 消息持久化，刷新页面后历史仍在 | Must |
| FR-25 | Markdown 渲染 + 代码块高亮 + 一键复制 | Must |
| FR-26 | 多轮上下文：默认携带最近 N 轮（可配置，默认 10 轮） | Must |
| FR-27 | 生成中状态提示（打字动画 / loading） | Must |
| FR-28 | 失败重试（网络错误 / 模型报错） | Should |
| FR-29 | 重新生成上一条回复 | Could |

#### （5）UI 与体验
| 编号 | 需求描述 | 优先级 |
|---|---|---|
| FR-30 | 三栏布局：会话侧栏 / 消息区 / 输入区 | Must |
| FR-31 | 深色 / 浅色主题切换 | Should |
| FR-32 | 响应式适配（≥1280 桌面优先，兼容笔记本 1366×768） | Must |
| FR-33 | 空状态、加载态、错误态完整 | Must |
| FR-34 | 全局消息提示（成功 / 失败 Toast） | Must |

### 3.2 优先级划分

**MVP（第一版必须跑通）**
FR-01 ~ FR-06、FR-09 ~ FR-14、FR-16 ~ FR-18、FR-20 ~ FR-27、FR-30、FR-33、FR-34

**v1.1（打磨）**
FR-07、FR-15、FR-19、FR-28、FR-31、FR-32

## 四、界面设计

### 4.1 设计原则
- **克制**：以内容为主，界面元素退到背景
- **即时反馈**：每个异步操作都有 loading / 结果提示
- **一致性**：圆角、间距、色板统一 Token 化

### 4.2 页面结构

```
┌──────────┬──────────────────────────────────────┐
│ 侧边栏    │  顶栏：会话标题 | 模型下拉 | 用户菜单   │
│ + 新建    ├──────────────────────────────────────┤
│          │                                      │
│ 会话1     │           消息列表（滚动）             │
│ 会话2     │   ┌────────────────────┐             │
│ 会话3     │   │ 用户气泡（右）      │             │
│          │   └────────────────────┘             │
│          │   ┌────────────────────┐             │
│          │   │ AI 气泡（左，Markdown）│           │
│          │   └────────────────────┘             │
│ 用户头像  ├──────────────────────────────────────┤
└──────────┴──────────────────────────────────────┘
             输入框 | 发送 / 停止 | 字数
```

### 4.3 关键页面
1. **登录 / 注册页**：左侧品牌插画区，右侧表单，密码框带显隐切换
2. **聊天主界面**：上述三栏
3. **个人中心**：资料编辑卡 + 修改密码卡（独立 Tab 或分栏）
4. **模型管理抽屉**：列出全部模型及加载状态，可手动触发加载

## 五、非功能需求

### 5.1 性能
| 指标 | 目标 |
|---|---|
| 首屏加载 | < 2s（本地） |
| 消息列表渲染 100 条 | < 300ms |
| 本地模型首 token 延迟 | < 3s（1.5B~3B，8G 显存） |
| 远端模型首 token 延迟 | 取决于 API，通常 < 2s |
| 并发 | 单卡串行推理，请求排队，超时 120s |

### 5.2 安全
- 密码 bcrypt（cost=12）存储；RSA-2048 传输加密
- JWT 签名密钥从环境变量读取，不硬编码
- 所有会话/消息接口校验资源归属，防越权（IDOR）
- SQL 注入：全部走 ORM 参数化
- XSS：Markdown 渲染白名单过滤，禁用 raw HTML
- CORS 白名单限定前端域名

### 5.3 兼容性
- Chrome / Edge 100+
- Python 3.11、MySQL 5.7
- 显存 8GB 可跑 1.5B–3B（bf16）；7B 需 4bit 量化（可选增强）

### 5.4 可维护性
- 前后端分离，接口契约固定
- 模型接入抽象为 Provider，新增模型只加配置
- 关键路径有日志，错误可定位

## 六、验收标准

1. 注册 → 登录 → 进入聊天界面全流程通畅
2. 数据库中 `users.password` 为 bcrypt 哈希；抓包看不到明文密码
3. 新建 / 重命名 / 删除会话均生效且刷新后保持
4. 同一会话内切换「本地模型 ↔ 远端模型」，历史保留，新消息由新模型生成
5. 本地 .pt / LoRA 模型成功加载并**真实推理出中文回复**
6. 流式输出可见逐字效果，停止按钮可中断
7. 个人资料可修改并持久化；改密码后旧密码不可登录
8. 页面在 1366×768 下无横向滚动、无错位
9. 前端已部署到 Cloudflare Pages / Vercel，可通过公网域名访问

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 8G 显存不足 | 模型加载 OOM | 优先 1.5B/3B；提供 4bit 量化开关；加载失败给明确提示 |
| transformers 与 torch 版本冲突 | 模型完全无法加载 | 独立 venv 锁定版本（见 TECH_DESIGN） |
| MySQL 5.7 编码问题 | 中文乱码 | 建库指定 utf8mb4，连接串显式 charset |
| 远端 API Key 未配置 | 远端模型不可用 | 降级为仅本地模型，前端置灰并提示 |
| 后端只能跑本机 | 公网访问受限 | 前端上 Pages，后端本机 + 内网穿透 |
